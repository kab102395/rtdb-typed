# rtdb-typed 0.3.0 plan

## Release theme

**First-class typed realtime events.**

`0.3.0` should make realtime Firebase usage safe and ergonomic without pretending that partial RTDB patches are complete Rust models.

This release establishes the event contract that `rtdb-sync` can depend on.

## Primary goals

- define correct typed semantics for Firebase `Put` and `Patch` events;
- expose a stable typed streaming API;
- preserve Firebase-specific event meaning instead of hiding it;
- add local SSE contract tests;
- add emulator-backed realtime tests;
- stress-test realtime event delivery and typed state conversion locally;
- keep reconnection/state ownership out of `rtdb-typed`.

## Typed event model

The current shape where both `Put` and `Patch` deserialize into the same full `T` is not sufficient for production semantics.

A Firebase `Patch` may contain only changed fields. Therefore the public model must distinguish complete replacement data from partial update data.

Target conceptual API:

```text
TypedEvent<T>
  Put {
    path,
    data
  }
  Patch {
    path,
    patch
  }
  KeepAlive
  Cancel
```

### Put semantics

A `Put` represents a complete value replacement at the event path.

The API should support deletion/null correctly. One acceptable shape is:

```text
Put {
  path: String,
  data: Option<T>
}
```

where `None` represents Firebase `null`/deletion.

If another representation is chosen, deletion semantics must still be explicit and strongly tested.

### Patch semantics

Do not deserialize patch payloads directly into full `T`.

Introduce a partial-update abstraction such as `TypedPatch` or `TypedPatch<T>`.

The patch abstraction should preserve the original JSON object and provide safe helpers such as:

- inspect raw patch JSON;
- deserialize a field into a requested type;
- test whether a field exists;
- iterate changed keys;
- optionally apply a patch to existing JSON/model state where semantics are well-defined.

Avoid code generation or reflection-heavy ORM behavior in this release.

## Stream API

Target conveniences:

- `TypedClient::stream<T>(path)`;
- `TypedQuery<T>::stream()`;
- stable `TypedEvent<T>`;
- stable patch abstraction;
- direct propagation of upstream stream errors through `TypedError`;
- clean stream termination on Firebase `Cancel`;
- preservation of `KeepAlive`.

`rtdb-typed` should convert events only. It must not own indefinite reconnect loops or synchronized application state.

## Event conversion contract

Create an internal conversion layer from:

```text
rtdb_rs::RtdbEvent
```

to:

```text
rtdb_typed::TypedEvent<T>
```

Test conversion independently from networking.

Required cases:

- full-object `Put`;
- scalar `Put`;
- collection/map `Put`;
- null/deletion `Put`;
- partial-object `Patch`;
- nested patch;
- malformed typed payload;
- `KeepAlive`;
- `Cancel`.

## Testing plan

### Layer 1: pure event conversion tests

No network.

Feed synthetic `rtdb_rs::RtdbEvent` values into the typed conversion layer.

Verify:

- complete values deserialize into `T`;
- null PUT semantics;
- patch payloads remain partial;
- malformed payloads produce deterministic typed errors;
- keepalive/cancel survive conversion unchanged.

### Layer 2: local mock SSE server

Implement a localhost SSE test server capable of emitting realistic Firebase event frames.

Test:

- initial `put` event;
- subsequent `put`;
- partial `patch`;
- multiple events in one connection;
- chunk boundaries splitting SSE lines;
- CRLF handling;
- keep-alive events;
- cancel events;
- malformed JSON payloads;
- stream closure;
- filtered stream URL/query behavior.

This validates the complete local path:

```text
mock SSE server -> rtdb-rs parser -> rtdb-typed conversion
```

without contacting Firebase.

### Layer 3: local Firebase RTDB emulator

Once namespace/config support exists in `rtdb-rs`, use the local emulator for true end-to-end realtime behavior.

Required cases:

- initial typed `Put` after stream connect;
- full overwrite produces typed `Put`;
- PATCH produces partial typed patch;
- delete produces null/deletion PUT semantics;
- child-path stream;
- filtered stream;
- multiple sequential events;
- concurrent streams;
- stream cancellation/closure behavior where the emulator can reproduce it.

## 0.3.0 realtime stress suite

The emulator is not just a smoke-test dependency. Use it to exercise realtime behavior aggressively before release.

### Standard stress profile

Target:

```text
24 simultaneous typed streams
40 writes/patches per stream root
```

Suggested topology:

```text
stress/<run-id>/streams/<stream-id>
```

For each stream:

1. connect and verify initial event;
2. issue alternating PUT and PATCH operations;
3. verify event ordering where Firebase guarantees it;
4. validate every event's typed data or patch content;
5. issue a delete and verify deletion semantics;
6. terminate stream cleanly.

This yields roughly 960 mutation-driven realtime event sequences plus initial and deletion events in one run.

### Fan-out profile

Add a second test where many subscribers watch the same path:

```text
32 subscribers
100 mutations on one shared root
```

Verify that each subscriber observes the expected event count and payload progression.

### Multi-path profile

Add a manual heavier profile:

```text
64 concurrent streams
100 mutations per stream root
```

Keep this ignored/manual if necessary.

The stress harness should record:

- stream count;
- event count;
- mutation count;
- parse/conversion failures;
- missed/extra events;
- elapsed time;
- cleanup outcome.

Do not claim emulator results as production capacity numbers. The purpose is semantic and concurrency confidence.

## rtdb-sync compatibility requirement

`0.3.0` is the contract release for `rtdb-sync`.

Before publishing, verify that the event API is sufficient for a downstream sync crate to:

- hydrate initial state;
- distinguish replacement from patch;
- represent deletion;
- apply partial patches;
- observe keepalive/cancel;
- propagate typed failures.

Do not add sync state management to this crate merely to make that downstream use case work.

## Documentation requirements

Before publishing `0.3.0`:

- document Firebase event semantics precisely;
- explain why PATCH is not a full `T`;
- show complete stream examples;
- show deletion/null examples;
- show patch inspection/application examples;
- document filtered typed streams;
- update README and CHANGELOG;
- include a migration note from any `0.1.x/0.2.x` provisional event API.

## Release gates

`0.3.0` is ready when:

- pure event-conversion tests pass;
- mock SSE contract tests pass;
- emulator realtime integration tests pass;
- standard realtime stress profile passes repeatedly;
- fan-out stress profile passes repeatedly;
- CI is green;
- rustdoc examples compile;
- `cargo package` succeeds;
- `cargo publish --dry-run` succeeds;
- `rtdb-sync` can consume the public event contract without reaching into crate internals;
- no automated test contacts production Firebase.

## Explicit non-goals

Do not add in `0.3.0`:

- automatic reconnect loops;
- exponential backoff;
- persistent local state;
- optimistic writes;
- offline queues;
- conflict resolution;
- token refresh orchestration.

Those belong primarily in `rtdb-sync` or `rtdb-admin`.

## Implementation status

The event contract and local conversion/mock-SSE implementation are complete:
`Put` carries `Option<T>`, `Patch` carries `TypedPatch`, and the stream layer
preserves keepalive/cancel while terminating after cancel. Emulator realtime
profiles are maintained in `tests/emulator_realtime.rs` and run only through
the demo-project local emulator runner.
