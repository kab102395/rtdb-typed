# rtdb-typed 0.2.0 plan

## Release theme

**Typed collections, typed queries, and deterministic data semantics.**

`0.2.0` should make `rtdb-typed` comfortable for normal application development without requiring callers to manually convert Firebase JSON into Rust types.

The crate remains a thin typed layer over `rtdb-rs`. It must not reimplement transport, authentication, Firebase URL construction, HTTP behavior, or SSE parsing.

## Primary goals

- make collection reads first-class;
- make query results first-class;
- define null and missing-node semantics explicitly;
- replace weak return shapes with stable typed wrappers where useful;
- expand local contract testing substantially;
- stress-test typed CRUD and typed queries against the local Firebase RTDB emulator;
- keep all default development and CI paths non-billable.

## Public API targets

### Typed collections

Introduce a first-class `FirebaseCollection<T>` abstraction instead of exposing raw `HashMap<String, T>` as the only collection contract.

Minimum capabilities:

- `len()`;
- `is_empty()`;
- `get(key)`;
- `contains_key(key)`;
- `keys()`;
- `values()`;
- `iter()`;
- `into_inner()`;
- `IntoIterator` where practical;
- serde-compatible deserialization from Firebase object maps.

The internal representation may use `HashMap<String, T>`, but the public wrapper gives the crate room to add Firebase-specific behavior later without changing the public contract.

### Collection methods

Target methods:

- `TypedClient::get_collection<T>()`;
- `TypedClient::get_optional_collection<T>()`;
- `TypedQuery<T>::send()` for arbitrary typed result shapes;
- `TypedQuery<T>::send_optional()`;
- `TypedQuery<T>::send_collection()`.

### Null semantics

The behavior must be documented and tested explicitly:

- `get<T>()`: Firebase `null` for a missing node becomes a typed deserialization error for non-nullable `T`;
- `get_optional<T>()`: Firebase `null` becomes `None`;
- `get_collection<T>()`: Firebase `null` becomes an empty `FirebaseCollection<T>`;
- `get_optional_collection<T>()`: Firebase `null` becomes `None`.

These semantics must not depend on accidental serde behavior.

### Push results

Replace the weak `String` return shape for push-key creation with a stable result type:

```text
PushResult
  key
  path (optional if derivable cleanly in 0.2.0)
```

The public API should allow future expansion without another breaking change.

## Query model

`TypedQuery<T>` should continue to mirror the underlying `rtdb-rs::GetBuilder` instead of inventing a second query DSL.

Support and test:

- `order_by_child`;
- `order_by_key`;
- `order_by_value`;
- explicit `OrderBy`;
- `limit_to_first`;
- `limit_to_last`;
- `start_at`;
- `end_at`;
- `equal_to`;
- `shallow` where the result shape is meaningful;
- query validation errors propagated from `rtdb-rs`.

## Error model

Review `TypedError` for public stability.

It should distinguish at minimum:

- upstream RTDB/transport errors;
- serde serialization/deserialization errors;
- malformed Firebase push responses;
- typed collection shape errors if any are needed beyond serde;
- future event-conversion errors without forcing a breaking redesign in `0.3.0`.

Avoid duplicating `rtdb-rs::RtdbError` variants.

## Testing plan

### Layer 1: pure unit tests

No network.

Cover:

- object deserialization;
- nested structs;
- optional fields;
- vectors;
- maps;
- scalar primitives;
- null behavior;
- invalid/missing required fields;
- collection conversion;
- empty collections;
- malformed push responses;
- round-trip serialization for representative models.

### Layer 2: local HTTP contract tests

Use only a localhost mock server.

Test the `rtdb-typed -> rtdb-rs -> HTTP` boundary for:

- typed GET;
- typed optional GET;
- typed PUT;
- typed PATCH;
- push-key POST;
- DELETE;
- query parameters;
- `orderBy`, limits, range filters, and equality filters;
- malformed JSON;
- wrong typed shape;
- Firebase `null`;
- non-success statuses propagated from `rtdb-rs`;
- malformed push-key payloads.

Contract tests should inspect the actual request line/query string so we know `rtdb-typed` is exercising the expected `rtdb-rs` URL behavior.

### Layer 3: local Firebase RTDB emulator

Use only the local emulator and a `demo-` project ID.

No production Firebase project is allowed in automated tests.

Required functional coverage:

- typed CRUD lifecycle;
- collection creation and retrieval;
- typed query filtering;
- typed range queries;
- empty query results;
- deletion and null behavior;
- multiple independent collection roots;
- concurrent readers and writers.

### 0.2.0 emulator stress suite

Create a repeatable stress harness that runs against the local RTDB emulator.

Initial target profile:

```text
32 concurrent workers
50 operation sequences per worker
```

Each worker should perform a mixed sequence such as:

```text
PUT typed record
GET and verify
PATCH subset of fields
GET and verify patched state
POST child and verify push key
query collection by indexed field
query range/limit path
```

That is at least 1,600 mixed operation sequences plus query traffic per run.

The test must:

- use a run-specific root to avoid collisions;
- verify every returned typed object;
- verify collection cardinality at the end;
- verify query result counts and values;
- clean up its root after success;
- print elapsed time and operation counts for diagnostics;
- avoid claiming production throughput or latency guarantees.

Add a second higher-load manual profile, for example:

```text
64 workers
100 operation sequences per worker
```

This may remain ignored/manual so CI does not become slow or flaky. The purpose is to actively exercise the emulator and typed API during development.

## Documentation requirements

Before publishing `0.2.0`:

- update crate-level rustdoc;
- document null semantics explicitly;
- document `FirebaseCollection<T>`;
- add typed collection examples;
- add typed query examples;
- document push-result semantics;
- update README API table;
- update CHANGELOG.

## Release gates

`0.2.0` is ready when:

- all unit tests pass;
- all local HTTP contract tests pass;
- the standard emulator integration suite passes;
- the standard emulator stress profile passes repeatedly;
- CI is green with `cargo fmt --check`, clippy with warnings denied, and tests;
- rustdoc examples compile;
- `cargo package` succeeds;
- `cargo publish --dry-run` succeeds;
- no automated test contacts a real Firebase project.

## Explicit non-goals

Do not add in `0.2.0`:

- automatic stream reconnection;
- local synchronized state;
- background tasks;
- offline caching;
- bidirectional sync;
- token refresh management;
- ORM-style persistence macros.

Those belong in later releases or companion crates.

## Completion record

The 0.2.0 implementation is complete in this repository:

- `FirebaseCollection<T>`, typed optional/collection queries, and `PushResult` are public.
- Unit and localhost contract coverage exercises conversion, nulls, malformed responses, CRUD, queries, and SSE.
- The standard emulator profile is 32 workers × 50 sequences; the manual profile is 64 × 100.
- Both emulator profiles use only the `demo-rtdb-typed` local namespace and pass with cleanup.
- Formatting, clippy, tests, rustdoc, examples, packaging, and publish dry-run are release gates.
